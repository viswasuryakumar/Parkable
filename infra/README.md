# Parkable SAM deployment

This directory contains a minimal SAM template for the Phase 2 API.

## Packaging note

No extra build artifact is required for the Lambda package. The existing shaded jar at `backend/target/parkable-cli.jar` already contains the Lambda handlers and their dependencies, so the template points `CodeUri` at that path directly.

## Deploy

1. Build the backend jar:
   ```powershell
   mvn -f backend/pom.xml package
   ```
2. Deploy with SAM:
   ```powershell
   sam deploy --template-file infra/template.yaml --config-file infra/samconfig.toml.example --guided
   ```

## Local API smoke test

If SAM CLI and Docker are available locally, you can run:

```powershell
sam local start-api --template-file infra/template.yaml
```

The API endpoints are:

- `POST /scan`
- `GET /check`
- `GET /nearby`
- `POST /report`
- `GET /reports` (owner-only, gated by `X-Admin-Secret`)

## Manual deploy (no SAM CLI)

This is the flow actually used to deploy `parkable-api` when the SAM CLI isn't
installed (e.g. no Docker/no admin rights):

```bash
mvn -f backend/pom.xml clean package -DskipTests
cd infra
aws cloudformation package \
  --template-file template.yaml \
  --s3-bucket parkable-photos \
  --output-template-file packaged.yaml
aws cloudformation deploy \
  --template-file packaged.yaml \
  --stack-name parkable-api \
  --capabilities CAPABILITY_IAM \
  --region us-west-1
```

`packaged.yaml` is generated output (gitignored) — never commit it, it's
regenerated by every package step.

**Windows/Git Bash note**: the AWS CLI arguments above that start with `/`
(SSM parameter names like `/parkable/db-url`, if you pass them explicitly)
get silently rewritten into Windows paths by Git Bash's MSYS path-conversion
layer, which breaks the AWS API call with a confusing "Parameter name must
be a fully qualified name" error. Prefix the command with
`MSYS_NO_PATHCONV=1` when that happens (PowerShell doesn't have this issue).

## Automated deploy (CI/CD)

`.github/workflows/backend.yml` runs the exact commands above automatically:

- **Every push/PR touching `backend/**` or `infra/**`**: runs the backend
  test suite (`mvn test`). No AWS credentials involved — this job can't
  touch the live stack.
- **Push to `main`, after tests pass**: a second job packages and deploys to
  `parkable-api`, but only after a human clicks **Approve** in the GitHub
  Actions tab — the job targets a `production` environment with a required
  reviewer, so nothing reaches the live stack unattended. Skip this gate
  by removing `environment: production` from the workflow if that
  friction stops being wanted.

**Secrets** (Settings → Secrets and variables → Actions):
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` — a dedicated IAM access key
  (not the one used for local `aws` CLI sessions), so it can be rotated or
  revoked independently. To rotate: `aws iam create-access-key --user-name
  parkable-dev`, update both secrets, then `aws iam delete-access-key
  --access-key-id <old-id> --user-name parkable-dev`.

`.github/workflows/mobile.yml` runs `npm run typecheck` and
`npx expo export --platform web` on any push/PR touching `mobile/**` — no
secrets needed, no deploy step (app-store publishing isn't set up).
